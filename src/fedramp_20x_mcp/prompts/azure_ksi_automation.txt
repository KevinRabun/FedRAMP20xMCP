# Azure/M365 KSI Automation Guide

## READ THIS BEFORE GENERATING ANY CODE

**What is a CR26 requirement and what is a design default.** CR26 defines 46 Key Security Indicators (KSIs) as outcomes you demonstrate with measures, plus FedRAMP rules (FRR). CR26 does NOT prescribe specific Azure settings. In particular CR26 sets no numeric log retention period, no required Key Vault SKU, no required zone redundancy and no required backup retention. The checklist below is a set of **recommended secure defaults** for Azure production systems that support the KSIs; when you generate code, cite the KSI or rule it supports, and where a value is a design choice, say so and make it a parameter your organization sets from its own policy and risk analysis. Use `get_ksi` and `get_frr_metadata` for the authoritative text.

**FRR CODE VALIDATION (use before deployment):**
- Run `analyze_frr_code` on generated infrastructure code to validate SCG (secure configuration) related rules
- Run `analyze_frr_family` with "CDS" to check Certification Data sharing support
- Run `analyze_frr_family` with "CMU" to validate cryptographic module use (CMU-CSO-CMD documents modules and their validation status; CMU-CSO-UVM requires validated modules by Class: MAY for A and B, SHOULD for C, MUST for D)
- Run `get_frr_evidence_automation` to set up automated evidence collection

**PRODUCTION-FIRST ENFORCEMENT:** All configurations, templates, and code are for **PRODUCTION systems**. Do not fall back to "common Azure defaults" without checking them against the defaults below.

**VERIFICATION PROCESS:**

**STEP 1: Before writing code, ask:**
1. Which KSI or rule does each setting support, and is the value a CR26 requirement or an organization-defined choice?
2. Are data services using customer-managed keys where your key-management KSI evidence relies on them (KSI-SVC-ASM)?
3. Do the Key Vault SKU and cryptographic modules match the CMU rules for your Certification Class?
4. Are diagnostic settings configured for every resource (KSI-MLA-OSM)?
5. Are Private Endpoints configured with public access disabled where appropriate (KSI-CNA-RNT)?

**STEP 2: If you are unsure, query the requirements first** (`get_ksi`, `get_frr_metadata`).

**STEP 3: After writing code, verify every value matches the defaults below or a documented organizational choice.**

### Recommended Secure Defaults (verify before code generation)

#### Encryption and Key Management (KSI-SVC-ASM, KSI-SVC-SIN)
- [ ] **Customer-managed keys (CMK)** for Storage, SQL, Cosmos DB, Disks, Event Hubs, Service Bus
  - Avoid `keySource: 'Microsoft.Storage'` (platform-managed keys) where you need key lifecycle control
  - Use `keySource: 'Microsoft.Keyvault'` with `keyvaultproperties`
  - Provide `keyVaultKeyUri` for Cosmos DB: `'https://{vault}.vault.azure.net/keys/{key}/{version}'`
- [ ] **Key Vault SKU**: `premium` gives HSM-backed keys. Choose the SKU that meets the CMU rules for your Class (CMU-CSO-UVM) and document the module (CMU-CSO-CMD)
- [ ] **enabledForDiskEncryption: true** when using Disk Encryption Sets
- [ ] **Separate encryption keys** per service type (storage-key, sql-key, cosmos-key, disk-key)
- [ ] **Managed Identity** with Key Vault permissions (unwrapKey, wrapKey, get)
- [ ] **Secret rotation** automated (KSI-SVC-ASM)

#### Logging and Monitoring (KSI-MLA-OSM, KSI-MLA-RVL, KSI-MLA-LET)
- [ ] **Log Analytics retention**: CR26 does not set a numeric value. Make it a parameter (`logRetentionDays`) driven by your policy and any applicable control parameters in the rules data (CTL section, for example AU family)
- [ ] **Diagnostic settings** for all Azure resources (Storage, SQL, VMs, Key Vault, Cosmos DB, etc.) linked to Log Analytics
- [ ] **Log categories**: enable the categories needed to meet your list of logged event types (KSI-MLA-LET)
- [ ] **Workspace SKU**: `PerGB2018` or `Committed` (avoid the Free tier for production)

#### Network Security (KSI-CNA-RNT through KSI-CNA-EIS)
- [ ] **Public access** `Disabled` for Storage, SQL, Key Vault, Cosmos DB, with Private Endpoints
- [ ] **TLS** 1.2 minimum (prefer 1.3 where supported); `minimumTlsVersion: 'TLS1_2'`
- [ ] **Private Endpoints** for PaaS services
- [ ] **Network Security Groups** with deny-by-default rules
- [ ] **Azure Firewall or Application Gateway** for inbound traffic

#### Identity and Access (KSI-IAM-APM through KSI-IAM-SUS)
- [ ] **Managed Identity** (`identity: { type: 'SystemAssigned' }`), no connection strings or API keys in code (KSI-IAM-SNU)
- [ ] **Disable local authentication** (`disableLocalAuth: true`) for Cosmos DB, Storage, Service Bus, Event Hubs
- [ ] **RBAC**: built-in roles, avoid Owner/Contributor on production (KSI-IAM-ELP)
- [ ] **Conditional Access** with phishing-resistant MFA (KSI-IAM-APM)
- [ ] **Privileged Identity Management** for admin roles (KSI-IAM-JIT)

#### Availability and Recovery (KSI-CNA-OFA, KSI-RPL family)
- [ ] **Availability zones / zone-redundant storage** (`Standard_ZRS` or `Standard_GZRS`) where your recovery objectives call for it (KSI-RPL-RRO, KSI-RPL-ABO)
- [ ] **Backup retention**: set from your defined recovery objectives; make it a parameter
- [ ] **Geo-replication** for critical data as your objectives require
- [ ] **Auto-failover** for multi-region deployments

## COMMENT FORMAT - INCLUDE KSI OR RULE IDs

Every compliance-related property should carry a comment with the KSI or rule ID it supports.

**Comment Format Template:**
```
// [KSI-XXX-NN] Description (NIST control if applicable)
propertyName: value
```
Use real KSI IDs from `list_ksi` (for example KSI-MLA-OSM). KSI-XXX-NN above is a placeholder.

**Bicep patterns:**

```bicep
// [KSI-MLA-OSM, KSI-MLA-RVL] Log retention is organization-defined; CR26 has no numeric rule (NIST AU-11)
retentionInDays: logRetentionDays

// [KSI-SVC-ASM] Customer-managed keys for encryption key lifecycle control (NIST SC-12)
keySource: 'Microsoft.Keyvault'

// [KSI-SVC-ASM] Premium SKU for HSM-backed keys (NIST SC-12; see CMU-CSO-UVM)
sku: { name: 'premium' }

// [KSI-IAM-APM, KSI-IAM-SNU] Disable local authentication, Entra ID only (NIST IA-2)
disableLocalAuth: true

// [KSI-CNA-RNT] Disable public access, use Private Endpoints only (NIST SC-7)
publicNetworkAccess: 'Disabled'

// [KSI-SVC-ASM] Customer-managed key URI for Cosmos DB encryption (NIST SC-12, SC-28)
keyVaultKeyUri: cosmosEncryptionKey.properties.keyUriWithVersion

// [KSI-CNA-ULN] Private Endpoint for secure network connectivity (NIST SC-7)
resource storagePrivateEndpoint 'Microsoft.Network/privateEndpoints@2023-11-01' = {

// [KSI-MLA-OSM] Diagnostic settings, send logs to Log Analytics (NIST AU-2, AU-11)
resource diagnostics 'Microsoft.Insights/diagnosticSettings@2021-05-01-preview' = {

// [KSI-RPL-ABO] Zone-redundant storage, aligned to recovery objectives (NIST CP-6, CP-9)
sku: { name: 'Standard_ZRS' }

// [KSI-CNA-RNT] Network Security Group with deny-by-default rules (NIST SC-7)
resource nsg 'Microsoft.Network/networkSecurityGroups@2023-11-01' = {

// [KSI-IAM-SNU] Managed Identity for authentication without credentials (NIST IA-5)
identity: { type: 'SystemAssigned' }

// [KSI-SVC-SIN] TLS 1.2 minimum for secure communications (NIST SC-8, SC-13)
minimumTlsVersion: 'TLS1_2'
```

**Terraform Comment Format:**
```hcl
# [KSI-MLA-OSM, KSI-MLA-RVL] Log retention is organization-defined; CR26 has no numeric rule (NIST AU-11)
retention_in_days = var.log_retention_days

# [KSI-SVC-ASM] Customer-managed keys for encryption key lifecycle control (NIST SC-12)
customer_managed_key {
  key_vault_key_id = azurerm_key_vault_key.storage.id
}

# [KSI-IAM-APM, KSI-IAM-SNU] Disable local authentication, Entra ID only (NIST IA-2)
local_authentication_disabled = true

# [KSI-CNA-RNT] Disable public access, use Private Endpoints only (NIST SC-7)
public_network_access_enabled = false

# [KSI-CNA-ULN] Private Endpoint for secure network connectivity (NIST SC-7)
resource "azurerm_private_endpoint" "storage" {
```

**Why This Matters:**
1. **Traceability**: Auditors can map each setting to a KSI or rule
2. **Maintainability**: Future developers understand why each setting exists
3. **Compliance evidence**: Comments serve as inline documentation for the Security Decision Record and Certification Data (CDS)
4. **Code reviews**: Reviewers can verify KSI alignment

## PATTERNS TO AVOID

```bicep
// Avoid: platform-managed keys where CMK lifecycle control is needed
keySource: 'Microsoft.Storage'

// Avoid: public access enabled
publicNetworkAccess: 'Enabled'

// Avoid: Cosmos DB without CMK when your KSI-SVC-ASM evidence relies on CMK
resource cosmosAccount 'Microsoft.DocumentDB/databaseAccounts@2023-11-15' = {
  properties: {
    // Missing keyVaultKeyUri property
  }
}

// Avoid: no diagnostic settings (KSI-MLA-OSM)
resource storageAccount 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  // Missing Microsoft.Insights/diagnosticSettings child resource
}
```

**Preferred patterns:**

```bicep
@description('Organization-defined log retention in days (CR26 sets no numeric value)')
param logRetentionDays int

retentionInDays: logRetentionDays

keySource: 'Microsoft.Keyvault'
keyvaultproperties: {
  keyname: storageEncryptionKey.name
  keyvaulturi: keyVault.properties.vaultUri
}

sku: { name: 'premium' }

publicNetworkAccess: 'Disabled'

resource cosmosAccount 'Microsoft.DocumentDB/databaseAccounts@2023-11-15' = {
  identity: { type: 'SystemAssigned' }
  properties: {
    keyVaultKeyUri: 'https://myvault.vault.azure.net/keys/cosmos-key/version'
  }
}

resource diagnostics 'Microsoft.Insights/diagnosticSettings@2021-05-01-preview' = {
  scope: storageAccount
  properties: {
    workspaceId: logAnalytics.id
    logs: [{ category: 'StorageWrite', enabled: true }]
  }
}
```

### KSI-IAM: Identity and Access Management (6 KSIs)

**KSI-IAM-APM: Adopting Passwordless Methods (phishing-resistant MFA)**

**Azure Services:**
- Microsoft Entra ID with Conditional Access
- FIDO2 security keys or Windows Hello for Business
- Microsoft Authenticator (passwordless)

**Automation:**
```powershell
# Connect to Microsoft Graph
Connect-MgGraph -Scopes "UserAuthenticationMethod.Read.All", "Policy.Read.All"

# Get MFA status for all users
$users = Get-MgUser -All
$mfaReport = @()

foreach ($user in $users) {
    $authMethods = Get-MgUserAuthenticationMethod -UserId $user.Id
    $hasFIDO2 = $authMethods | Where-Object { $_.AdditionalProperties.'@odata.type' -eq '#microsoft.graph.fido2AuthenticationMethod' }
    
    $mfaReport += [PSCustomObject]@{
        UserPrincipalName = $user.UserPrincipalName
        HasFIDO2 = ($hasFIDO2 -ne $null)
        MFAEnabled = $authMethods.Count -gt 1
    }
}

# Generate compliance report
$mfaReport | Export-Csv "mfa-compliance-$(Get-Date -Format yyyy-MM-dd).csv"
```

### Vulnerability Detection and Response (VDR, VER) and KSI-SCR-MON

**VDR-CSO-DET: Vulnerability Detection**

**Azure Services:**
- Microsoft Defender for Cloud
- Microsoft Defender for Containers
- GitHub Advanced Security (for code)

**Automation:**
```powershell
# Get vulnerability assessment findings from Defender for Cloud
$vulnerabilities = Get-AzSecurityTask | Where-Object { 
    $_.SecurityTaskParameters.Name -match "Vulnerability" 
}

# Generate a vulnerability report (fields per VER-RPT-VDT)
$vulnReport = $vulnerabilities | Select-Object @{
    Name = 'FindingId'; Expression = { $_.Name }
}, @{
    Name = 'Severity'; Expression = { $_.SecurityTaskParameters.Severity }
}, @{
    Name = 'Resource'; Expression = { $_.ResourceId }
}, @{
    Name = 'DetectedDate'; Expression = { $_.TimeGenerated }
}, @{
    Name = 'DueDate'; Expression = { 
        # Mitigation/remediation target per VDR-TFR-PVR (SHOULD). Days from evaluation, by Class,
        # Potential Agency Impact N-rating, and reachability/exploitability.
        # Values below are Classes A and B from the rule; read the rule for Class C and D tables.
        # Keys: IRVLEV = internet-reachable + likely exploitable, NIRVLEV = not internet-reachable + likely exploitable, NLEV = not likely exploitable
        $pvr = @{
            2 = @{ IRVLEV = 96; NIRVLEV = 160; NLEV = 192 }
            3 = @{ IRVLEV = 32; NIRVLEV = 64;  NLEV = 192 }
            4 = @{ IRVLEV = 8;  NIRVLEV = 32;  NLEV = 64 }
            5 = @{ IRVLEV = 4;  NIRVLEV = 8;   NLEV = 32 }
        }
        $nRating = [int]$_.SecurityTaskParameters.NRating            # estimated per VER-EVA-EPA
        $bucket  = if ($_.SecurityTaskParameters.LikelyExploitable -ne 'true') { 'NLEV' }
                   elseif ($_.SecurityTaskParameters.InternetReachable -eq 'true') { 'IRVLEV' } else { 'NIRVLEV' }
        $days = if ($pvr.ContainsKey($nRating)) { $pvr[$nRating][$bucket] } else { $null }   # N1 has no timeframe in the rule
        if ($days) { (Get-Date).AddDays($days) } else { $null }
    }
}

$vulnReport | Export-Csv "vuln-report-$(Get-Date -Format yyyy-MM-dd).csv"
```

### KSI-SVC: Service Configuration (8 KSIs)

**KSI-SVC-ASM: Automating Secret Management**

**Azure Services:**
- Azure Key Vault (Premium SKU gives HSM-backed keys)
- Managed Identity
- Azure Monitor

**Customer-Managed Keys (CMK): recommended design default**

CR26 does not mandate CMK. KSI-SVC-ASM (automating management, protection and regular rotation of digital keys, certificates and other secrets) and the NIST SC-12 control relate to key lifecycle control, and CMK is a common way to demonstrate it. Cryptographic module expectations are in the CMU rules (CMU-CSO-CMD documentation; CMU-CSO-UVM validated modules by Class).

**Why CMK is useful:**
- **Key lifecycle control**: rotation, revocation, versioning, BYOK
- **Key revocation**: platform-managed keys are controlled by Microsoft, with limited revocation capability
- **HSM-backed keys**: Key Vault Premium provides HSM-backed keys

**Resources where CMK applies:**
1. **Storage Accounts**: Use `keySource: 'Microsoft.Keyvault'` (not `'Microsoft.Storage'`)
2. **SQL Databases**: Configure TDE with customer-managed key
3. **Managed Disks**: Use Disk Encryption Sets with Key Vault key
4. **Cosmos DB**: Configure `keyVaultKeyUri` as **TOP-LEVEL property** (NOT inside encryption object)
5. **Azure Data Lake**: Use customer-managed key encryption

**⚠️ CRITICAL: Cosmos DB CMK Common Mistakes:**
- ❌ WRONG: `properties: { encryption: { keyVaultKeyUri: '...' } }` - NO encryption object exists
- ✅ CORRECT: `properties: { keyVaultKeyUri: '...' }` - keyVaultKeyUri is a direct property
- ❌ WRONG: `properties: { diagnosticLogSettings: {...} }` - This property doesn't exist
- ✅ CORRECT: Separate `Microsoft.Insights/diagnosticSettings` resource with `scope: cosmosDb`

**CMK Configuration Example (Bicep).** The examples below assume `param logRetentionDays int` (organization-defined; CR26 sets no numeric log retention).

## Private Endpoints Configuration (KSI-CNA-RNT, KSI-CNA-ULN)

**⚠️ WARNING: Setting `publicNetworkAccess: 'Disabled'` without Private Endpoints will make resources COMPLETELY INACCESSIBLE!**

**Configure Private Endpoints whenever you disable public access.**

### Why Private Endpoints are needed:

1. **Functional Requirement**: Resources are unreachable without Private Endpoints
2. **KSI-CNA-RNT**: Restricting Network Traffic (private connectivity for PaaS)
3. **KSI-CNA-ULN**: Using Logical Networking
4. **NIST SC-7**: Boundary Protection

## Evidence Collection Automation Framework

### Centralized Evidence Repository

**Azure Architecture:**
```
Evidence Collection Flow:
1. Automated Scripts (PowerShell/CLI/KQL) → 
2. Azure Functions (scheduled triggers) →
3. Azure Blob Storage (immutable, encrypted) →
4. Azure Purview (cataloging) →
5. Certification Data sharing via your trust center (CDS-CSO-UTC, CDS-TRC-PAC)
```

**Implementation:**
```powershell
# Create evidence storage with immutability
# Retention values are organization-defined (CR26 sets no numeric evidence retention period)
$EvidenceRetentionDays = 0   # SET from your retention policy
$ImmutabilityDays = 0        # SET from your retention policy

    -ResourceGroupName "rg-fedramp-evidence" `
    -Name "fedrampevidence" `
    -Location "eastus" `
    -SkuName "Standard_GRS" `
```
