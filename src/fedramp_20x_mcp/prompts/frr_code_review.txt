# FRR Code Review Guide

I'll help you review code for FedRAMP Rule (FRR) compliance under the FedRAMP Consolidated Rules for 2026 (CR26) using AST-powered semantic analysis.

## Review Process

### 1. Identify Review Scope

**What are you reviewing?**
- [ ] Single rule (analyze_frr_code)
- [ ] Entire family (analyze_frr_family)
- [ ] Comprehensive scan (analyze_all_frrs)

**What type of code?**
- [ ] Application Code (Python, C#, Java, TypeScript/JavaScript)
- [ ] Infrastructure as Code (Bicep, Terraform)
- [ ] CI/CD Pipelines (GitHub Actions, Azure Pipelines, GitLab CI)

### 2. Choose Your FRR Focus

CR26 has 17 FRR families and 245 rules. Many rules vary by Certification Class (A, B, C, D); check varies_by_class with `get_frr_metadata`.

**Most Common FRR Families for Code Reviews:**

**VDR (Vulnerability Detection and Response) and VER (Vulnerability Evaluation and Reporting):**
- VDR-CSO-DET: Vulnerability detection implementation
- VDR-CSO-ADT: Automated detection
- VDR-CSO-DAC: Detection after changes
- VDR-TFR-PVR: Mitigation and remediation timeframes (by Class, N-rating, reachability)
- VER-EVA-EIR: Evaluate internet-reachability
- VER-RPT-VDT: Vulnerability report fields
- VER-TFR-MHR: Monthly activity report
- Use: `analyze_frr_family("VDR", code, language)` and `analyze_frr_family("VER", code, language)`

**CDS (Certification Data Sharing):**
- CDS-CSO-PUB: Public information in human-readable and JSON formats
- CDS-CSO-CBF: Automated consistency between formats
- CDS-TRC-PAC: Documented programmatic access
- CDS-TRC-ACL: Access logging
- Use: `analyze_frr_family("CDS", code, language)`

**SCG (Secure Configuration Guide):**
- SCG-CSO-RSC: Recommended secure configuration
- SCG-CSO-SDF: Secure defaults
- SCG-ENH-EXP and SCG-ENH-API: Export and API capabilities for settings
- Use: `analyze_frr_family("SCG", code, language)`

**CMU (Cryptographic Module Use):**
- CMU-CSO-CMD: Cryptographic module documentation
- CMU-CSO-CAT: Agency tenants configured with validated modules by default
- CMU-CSO-UVM: Using validated cryptographic modules (by Class)
- Use: `analyze_frr_family("CMU", code, language)`

**CCM (Collaborative Continuous Monitoring):**
- CCM-OCR-AVL: Ongoing Certification Report every 3 months
- CCM-OCR-FBM: Feedback mechanism
- CCM-QTR-MTG: Quarterly Review meeting (by Class)
- Use: `analyze_frr_family("CCM", code, language)`

### 3. Run FRR Analysis

**For Specific Rule:**
```
> analyze_frr_code with frr_id="VDR-CSO-DET" and code="[paste code]" and language="python"
```

**For Entire Family:**
```
> analyze_frr_family with family="VDR" and code="[paste code]" and language="bicep"
```

**For Comprehensive Review:**
```
> analyze_all_frrs with code="[paste code]" and language="terraform"
```

### 4. Review Findings

**Finding Severity Levels (tool output ranking, not a CR26 concept):**
- **Critical**: Must fix before deployment (blocking compliance issue)
- **High**: Security risk or major compliance gap
- **Medium**: Configuration improvement needed
- **Low**: Best practice recommendation

**Review Checklist:**
- [ ] Understand each finding's FRR rule reference and its force (MUST, SHOULD, MAY)
- [ ] Check NIST 800-53 control mappings
- [ ] Review remediation recommendations
- [ ] Identify quick wins vs. architectural changes

### 5. Address Findings

**Remediation Workflow:**
1. **Prioritize MUST rules and blocking findings**
2. **Review Azure-specific guidance**
3. **Implement fixes**
4. **Re-run analysis**
5. **Document decisions** in the Security Decision Record (explain how the rule is followed, or the reason and resulting risk of not following it)

**Get Additional Context:**
- Rule details: `get_frr_metadata("VDR-CSO-DET")`
- Evidence automation: `get_frr_evidence_automation("VDR-CSO-DET")`
- Family overview: `list_frrs_by_family("VDR")`

### 6. Integration with Pull Requests

**Option 1: Targeted Family Review**
```yaml
# .github/workflows/frr-review.yml
- name: VDR Compliance Check
  run: |
    analyze_frr_family("VDR", changed_files, "python")
```

**Option 2: Comprehensive FRR Scan**
```yaml
# Azure Pipelines
- task: FRRComplianceCheck@1
  inputs:
    analysisType: 'all_frrs'
    codeFiles: '$(Build.SourcesDirectory)'
    language: 'bicep'
```

**Option 3: Specific Rules**
```yaml
# GitLab CI
frr-check:
  script:
    - analyze_frr_code("CDS-CSO-PUB", "$CI_COMMIT_FILE", "python")
    - analyze_frr_code("VDR-CSO-DET", "$CI_COMMIT_FILE", "python")
```

## Common Scenarios

### Scenario 1: Vulnerability Management Review (VDR, VER)
**Goal:** Ensure the CI/CD pipeline implements vulnerability detection and reporting

**Steps:**
1. `analyze_frr_family("VDR", pipeline_yaml, "github-actions")`
2. Check for:
   - VDR-CSO-DET: Scanning tools (Trivy, Defender, Qualys)
   - VDR-CSO-DAC: Detection on new or significantly changed resources
   - VER-EVA-EIR and VER-EVA-ELX: Reachability and exploitability evaluation
   - VER-TFR-MAV: Accepted-vulnerability tracking after 192 days
3. Review findings and implement recommended tools
4. Re-run analysis to verify compliance

### Scenario 2: Certification Data Sharing Review (CDS)
**Goal:** Validate trust center and Certification Data implementation

**Steps:**
1. `analyze_frr_family("CDS", api_code, "python")`
2. Check for:
   - CDS-CSO-PUB: JSON public information
   - CDS-TRC-PAC: Programmatic access with authentication
   - CDS-TRC-ACL: Access logging
   - CDS-CSO-CBF: Consistency automation between formats
3. Review Azure API Management recommendations

### Scenario 3: Infrastructure Security Review (SCG + CMU)
**Goal:** Ensure secure configuration and cryptographic compliance

**Steps:**
1. `analyze_frr_family("SCG", bicep_code, "bicep")`
2. `analyze_frr_family("CMU", bicep_code, "bicep")`
3. Check for:
   - SCG-CSO-RSC and SCG-CSO-SDF: Secure configuration and defaults
   - CMU-CSO-CMD: Documented cryptographic modules
   - CMU-CSO-CAT: Validated modules by default for agency tenants
   - KSI-SVC-ASM: Azure Key Vault integration
4. Apply hardening recommendations

### Scenario 4: Comprehensive Pre-deployment Review
**Steps:**
1. `analyze_all_frrs(application_code, "csharp")`
2. `analyze_all_frrs(infrastructure_code, "terraform")`
3. `analyze_all_frrs(cicd_pipeline, "azure-pipelines")`
4. Review findings across all FRR families
5. Create remediation plan by priority
6. Track progress using `get_frr_implementation_status()`

## Tips for Effective FRR Code Reviews

**Best Practices:**
- Run FRR analysis early in development (shift-left security)
- Integrate FRR checks into PR workflows
- Document process-based rules separately; not all rules are code-detectable
- Combine FRR and KSI analysis for comprehensive coverage
- Use family-specific analysis for targeted reviews
- Re-run analysis after fixes to verify resolution

**Common Pitfalls to Avoid:**
- Skipping VDR and VER in CI/CD pipelines
- Ignoring CDS requirements for trust center and Certification Data
- Missing CMU cryptographic requirements
- Not validating SCG baselines in IaC
- Treating all findings as equal priority
- Fixing symptoms without addressing root causes
