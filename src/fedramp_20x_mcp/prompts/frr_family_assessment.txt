# FRR Family Assessment Guide

I'll help you conduct an FRR family assessment for your system under the FedRAMP Consolidated Rules for 2026 (CR26, version 2026.10.13.01).

## Overview

CR26 has **245 rules** across **17 FRR families**. Each family addresses a compliance area. Rule IDs have the form FAMILY-GROUP-NAME (for example VDR-CSO-DET); the group (CSO, TFR, EVA, ...) is the family's subset. Many rules vary by Certification Class (A, B, C, D); read `varies_by_class` with `get_frr_metadata`.

Families (rule counts): AFC (16), AGU (20), CCM (19), CDS (21), CMU (3), CPO (5), FRC (28), IEC (8), IVV (20), MAS (5), MKT (12), REC (16), SCG (9), SCN (17), SDR (5), VDR (18), VER (23).

Effective dates differ by family (see each family's effective block in the rules data): for example AFC 2026-01-05, SCG 2026-03-01, AGU, MKT and REC 2026-07-04, VDR and VER required 2026-12-07 (mandated by CISA BOD 26-04).

## Choose Your Assessment Scope

### 1. VDR and VER - Vulnerability Detection, Evaluation, Response and Reporting
**Purpose:** Detect, evaluate, mitigate, remediate and report vulnerabilities.

**Groups:** VDR-CSO (provider responsibilities), VDR-TFR (timeframes), VER-EVA (evaluation), VER-RPT (reporting), VER-TFR (timeframes).

**Assessment Questions:**
1. Is detection automated and run after changes (VDR-CSO-ADT, VDR-CSO-DAC)?
2. Do you track mitigation and remediation against VDR-TFR-PVR timeframes for your Class, N-rating and reachability?
3. Do you evaluate exploitability, internet-reachability and Potential Agency Impact (VER-EVA-ELX, VER-EVA-EIR, VER-EVA-EPA)?
4. Do you follow CISA KEV due dates (VDR-TFR-KEV)?
5. Do you report at least monthly and mark accepted vulnerabilities after 192 days (VER-TFR-MHR, VER-TFR-MAV)?

**Start Assessment:**
```
> analyze_frr_family with family="VDR" and code="[your CI/CD pipeline]" and language="github-actions"
> list_frrs_by_family with family="VDR"
> list_frrs_by_family with family="VER"
```

### 2. CDS - Certification Data Sharing
**Purpose:** Trust center, public information, programmatic access to Certification Data.

**Groups:** CDS-CSO (provider), CDS-TRC (trust centers), CDS-UTC (using a trust center).

**Assessment Questions:**
1. Do you use a FedRAMP-compatible trust center (CDS-CSO-UTC)?
2. Is public information available in human-readable and JSON formats (CDS-CSO-PUB)?
3. Is programmatic access documented (CDS-TRC-PAC)?
4. Is consistency between formats automated (CDS-CSO-CBF)?
5. Is access logged and summarized (CDS-TRC-ACL)?

4. Do you offer comparison, export or API access to settings (SCG-ENH-CMP, SCG-ENH-EXP, SCG-ENH-API)?

### 5. SCN - Significant Change Notification
**Purpose:** Change evaluation, notification and records.

**Groups:** SCN-CSO, SCN-ADP (adaptive), SCN-RTR (routine recurring), SCN-TRF (transformative).

1. Do you evaluate changes and classify them (SCN-CSO-EVA)?
2. Do you keep auditable records (SCN-CSO-MAR)?
3. Do you notify within the SCN-ADP and SCN-TRF timeframes?
4. Do you keep 12 months of notifications in human-readable and JSON formats (SCN-CSO-HIS, SCN-CSO-HRM)?

**Purpose:** Ongoing Certification Reports and Quarterly Reviews.

**Groups:** CCM-OCR (Ongoing Certification Reports), CCM-QTR (Quarterly Reviews), CCM-AGM (agency guidance).

**Assessment Questions:**

3. Do you host a Quarterly Review every 3 months where required for your Class (CCM-QTR-MTG)?
4. Do you supply registration information and publish the next review date (CCM-QTR-REG, CCM-QTR-NRD)?

## Comprehensive Assessment Workflow

### Phase 1: Discovery
1. `list_frrs_by_family with family="[chosen family]"`
2. Identify code-detectable versus process-based rules and note NIST 800-53 control mappings
3. `get_frr_metadata with frr_id="VDR-CSO-DET"` for key rules

### Phase 2: Code Analysis
1. Run family-specific analysis against application code, IaC and CI/CD
2. Review findings by priority (tool ranking)
3. Document gaps and compliant areas; identify areas needing manual review

### Phase 3: Evidence Planning
1. `get_frr_evidence_automation with frr_id="VDR-CSO-DET"`
2. Plan evidence collection infrastructure (Log Analytics, Storage, Monitor) and schedules. CR26 sets no numeric evidence or log retention period; the exceptions are specific rules (for example CDS-TRC-ACL access summaries for at least six months and SCN-CSO-HIS 12 months of notifications). Choose retention for everything else from your own policy.
3. Design evidence artifacts (use the rule's artifacts field where present) and storage with access controls

### Phase 4: Implementation
1. Prioritize MUST rules first
2. Implement evidence automation and dashboards
3. Document compliance in the Security Decision Record (SDR-CSO-FRR)

### Phase 5: Validation
1. Re-run analysis after fixes
2. Verify blocking findings resolved
3. Track status: `get_frr_implementation_status`

## Family-Specific Best Practices

### VDR and VER
- Automated detection in CI/CD and for deployed resources
- Container scanning (Trivy, Defender for Cloud)
- Timeframe tracking against VDR-TFR-PVR and VDR-TFR-KEV
- Monthly reporting (VER-TFR-MHR)
- Azure services: Defender for Cloud, Log Analytics, Azure DevOps, Azure Policy

### CDS
- Trust center with documented programmatic access
- JSON valid against FedRAMP schemas (FRC-CSO-JSN)
- Access logging and agency access inventory (CDS-TRC-ACL, CDS-TRC-AAI)
- Azure services: API Management, Azure Functions, Application Insights, Key Vault

### SCG
- Settings as code (Bicep/Terraform), Azure Policy for drift enforcement
- Azure services: Azure Policy, Resource Graph, Automation

### CMU
- Validated modules where required for your Class
- Azure Key Vault Premium or Managed HSM
- Azure services: Key Vault Premium, Managed HSM, Storage encryption
