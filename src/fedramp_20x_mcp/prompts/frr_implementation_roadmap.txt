# FRR Implementation Roadmap

I'll help you create a strategic roadmap for implementing FedRAMP Rules (FRR) under the FedRAMP Consolidated Rules for 2026 (CR26, version 2026.10.13.01).

## Executive Summary

**CR26 includes 245 FRR rules** across 17 families (AFC, AGU, CCM, CDS, CMU, CPO, FRC, IEC, IVV, MAS, MKT, REC, SCG, SCN, SDR, VDR, VER) plus 46 Key Security Indicators in 10 families. Many rules vary by Certification Class (A, B, C, D) and some only apply to 20x or Rev5; first work out which rules apply to you, then phase the work. The week numbers below are an illustrative planning aid, not CR26 requirements.

**Key Principles:**
- Start with code-detectable rules for quick automation wins
- Build foundational infrastructure before advanced capabilities
- Prioritize VDR/VER and CDS (high audit visibility; VDR and VER are required from 2026-12-07)
- Integrate FRR compliance into existing DevOps workflows
- Automate evidence collection from day one

## Implementation Phases

### Phase 1: Foundation and Quick Wins (illustrative: weeks 1-4)

**Goal:** Establish vulnerability management, secure configuration and cryptographic module documentation

**Priority Families:**
1. **VDR and VER (Vulnerability Detection, Response, Evaluation and Reporting)**
2. **SCG (Secure Configuration Guide)**
3. **CMU (Cryptographic Module Use)**

**Implementation Steps:**

**VDR foundation**
- [ ] Implement VDR-CSO-DET: Vulnerability detection in CI/CD and for deployed resources
  - Tools: Trivy, Defender for Cloud, or Qualys
  - Evidence: Scan results exported to Azure Storage
  ```
  > analyze_frr_code with frr_id="VDR-CSO-DET" and code="[CI/CD pipeline]" and language="github-actions"
  > get_frr_evidence_automation with frr_id="VDR-CSO-DET"
  ```

- [ ] Implement VDR-TFR-PVR tracking: mitigation and remediation timeframes
  - Timeframes depend on Certification Class, N-rating and internet-reachability (read the rule's varies_by_class table); there are no fixed Critical/High/Moderate buckets
  - Track KEV due dates (VDR-TFR-KEV) and the 192-day accepted-vulnerability threshold (VER-TFR-MAV)
  - Alert on approaching deadlines

- [ ] Implement VER-EVA-*: evaluate exploitability, internet-reachability and Potential Agency Impact (VER-EVA-ELX, VER-EVA-EIR, VER-EVA-EPA)

- [ ] Implement VER-TFR-MHR and VER-RPT-VDT: monthly reporting with the required fields

**SCG and CMU foundation**
- [ ] Implement SCG-CSO-RSC: Secure configuration recommendations
  - Apply CIS Benchmarks via Azure Policy
  - Configure drift detection
  ```
  > analyze_frr_family with family="SCG" and code="[Bicep/Terraform]" and language="bicep"
  ```

- [ ] Implement CMU-CSO-CMD: Document cryptographic modules and their validation status
  - Use validated modules where your Class requires it (CMU-CSO-UVM: MAY for A and B, SHOULD for C, MUST for D)
  - Default agency tenants to validated modules (CMU-CSO-CAT)
  ```
  > analyze_frr_family with family="CMU" and code="[infrastructure]" and language="terraform"
  ```

**Evidence automation setup**
- [ ] Deploy evidence collection infrastructure (Log Analytics, Azure Storage, Azure Functions, Event Grid). CR26 sets no numeric retention period for evidence or logs; set retention from your own policy, except where a rule states one (for example CDS-TRC-ACL access summaries for at least six months)
- [ ] Configure evidence collection for Phase 1 rules (scan results, remediation tracking, configuration baselines, cryptographic module lists)

**Phase 1 Success Criteria:**
- Vulnerability detection in all CI/CD pipelines and monthly reporting working
- Secure configuration baselines applied
- Cryptographic modules documented
- Evidence automatically collected and stored

### Phase 2: Certification Data Sharing and Monitoring (illustrative: weeks 5-8)

**Goal:** Implement Certification Data sharing and Ongoing Certification

**Priority Families:**
4. **CDS (Certification Data Sharing)**
5. **CCM (Collaborative Continuous Monitoring)**

**Implementation Steps:**

**CDS**
- [ ] Implement CDS-CSO-PUB: Public information in human-readable and JSON formats
  ```
  > analyze_frr_code with frr_id="CDS-CSO-PUB" and code="[API code]" and language="python"
  > get_frr_evidence_automation with frr_id="CDS-CSO-PUB"
  ```
- [ ] Implement CDS-CSO-UTC and CDS-TRC-PAC: FedRAMP-compatible trust center with documented programmatic access
- [ ] Implement CDS-TRC-ACL and CDS-TRC-AAI: access logging and agency access inventory
- [ ] Implement CDS-CSO-CBF: automation keeping human-readable and machine-readable formats consistent
- [ ] Validate JSON against FedRAMP schemas (FRC-CSO-JSN)

**CCM**
- [ ] Implement CCM-OCR-AVL: Ongoing Certification Report every 3 months
  - Include the information listed in the rule (changes to Certification Data, planned changes, accepted vulnerabilities, transformative changes, agencies using the product, reportable incidents)
  ```

  ```
- [ ] Implement CCM-OCR-NRD, CCM-OCR-FBM, CCM-OCR-AFS: next report date, feedback mechanism, anonymized feedback summary
- [ ] Implement CCM-QTR-MTG (strength varies by Class) with CCM-QTR-REG and CCM-QTR-NRD
- [ ] Implement CDS-CSO-HAD: snapshots of Certification Data aligned to each Ongoing Certification Report

**Phase 2 Success Criteria:**
- Certification Data available via trust center and programmatic access
- Ongoing Certification Report process automated
- Quarterly Review logistics in place

## Prioritization Framework

### High Priority (Implement First)
Criteria: high audit visibility, MUST force, required for certification, strong automation potential.

**Top 10 rules to implement:**
1. VDR-CSO-DET: Vulnerability detection
2. VDR-CSO-RES: Vulnerability response
3. SCG-CSO-RSC: Secure configuration
4. CMU-CSO-CMD: Cryptographic module documentation
5. CDS-CSO-PUB: Public information in JSON
6. CCM-OCR-AVL: Ongoing Certification Report
7. VER-TFR-MHR: Monthly vulnerability reporting
8. CDS-CSO-UTC: Trust center
9. SCN-CSO-EVA: Change evaluation
10. MAS-CSO-IIR: Minimum Assessment Scope

### Medium Priority
- VDR-TFR-PVR timeframe tracking by Class
- CDS-TRC-ACL access logging
- CCM-QTR-MTG quarterly review automation
- SCN-CSO-INF notification content

### Lower Priority
- Process-based rules (REC, MKT, AGU as applicable)
- Rules with SHOULD or MAY force for your Class

## Common Challenges and Solutions

### "Too many rules to implement"
Identify the rules that apply to your Class and Type, then focus on code-detectable ones first.

### "Don't know where to start"
Follow the phases: VDR/VER + SCG + CMU, then CDS + CCM, then SCN + MAS + IVV, then IEC + AFC.

### "Evidence collection is manual"
Use `get_frr_evidence_automation()` for every rule and automate from day one; the rule's artifacts field lists what assessors expect.

### "Rules overlap"
Analyze by family, implement shared capabilities once, and leverage KSI alignment (rules reference related KSIs and controls).

### "How do I know if my implementation is compliant?"
Use FRR analysis tools in CI/CD, run regular family assessments, and record decisions in the Security Decision Record.

## Integration with KSI Implementation

- **KSIs** (46 in 10 families) are security outcomes you demonstrate with measures
- **FRRs** (245 rules) are obligations on providers, agencies, assessors and FedRAMP
- Many FRRs relate to specific KSIs and NIST controls

**Example: Vulnerability management**
- Implement VDR-CSO-DET and VDR-CSO-RES
- Relate to KSI-SCR-MON (monitoring supply chain risk) and KSI-MLA-EVC (evaluating configurations)
- Share evidence collection across them
