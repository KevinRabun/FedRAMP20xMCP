I'll help you generate documentation templates for FedRAMP compliance under the FedRAMP Consolidated Rules for 2026 (CR26, version 2026.10.13.01).

# Documentation Generator for CR26

**PRODUCTION-FIRST ASSUMPTION:** All documentation and system descriptions assume **PRODUCTION systems** with full security controls unless explicitly stated otherwise. FedRAMP Certification applies to production environments processing federal data.

**Important Note on formats:** CR26 replaces the System Security Plan (SSP) with the **Certification Package Overview** (CPO) and the **Security Decision Record** (SDR). Both MUST be supplied in human-readable and JSON formats (CPO-CSO-OVR, SDR-CSO-FRR), and JSON MUST validate against the FedRAMP JSON schema when a rule defines one (FRC-CSO-JSN). OSCAL is not required. CR26 does not require a POA&M or a SAR. The JSON skeletons below are illustrative; always validate against the official schemas referenced in the rules data (schema.url fields).

## Certification Package Overview Template (CPO-CSO-OVR, CPO-CSO-MTD)

The overview MUST include the information required by CPO-CSO-MTD, CDS-CSO-PUB, CDS-CSO-SVC, CDS-CSO-IRP, MAS-CSO-IIR, MAS-CSO-FLO, MAS-CSO-TPR, CMU-CSO-CMD and IVV-CSO-ICP (rules that do not apply to your Class or Type are not required).

### 1. Metadata (CPO-CSO-MTD)
```json
{
  "certification-package-overview": {
    "responsible-official": {
      "name": "[Name]",
      "title": "[Title]",
      "contact": "security@example.com"
    },
    "version": "1.0.0",
    "last-updated": "YYYY-MM-DDTHH:MM:SSZ",
    "update-source": "[automation or person that produced the update]",
    "fedramp-id": "FR-########"
  }
}
```
Always include the FedRAMP ID in all Certification Data once assigned (CDS-CSO-FID).

### 2. Cloud Service Offering and Scope (MAS)
```json
{
  "cloud-service-offering": {
    "name": "[Your System Name]",
    "description": "[Overall service description including federal customer data handling]",
    "service-model": "SaaS",
    "deployment-model": "[Deployment model]",
    "services": [
      {
        "name": "[Service name aligned with public marketing materials]",
        "security-category": "[category]",
        "in-minimum-assessment-scope": true
      }
    ],
    "information-resources": [
      {
        "id": "AST-001",
        "type": "machine-based",
        "handles-federal-customer-data": true,
        "third-party": false
      }
    ],
    "information-flows": "[Machine-readable output of permitted connections between components (MAS-CSO-FLO)]",
    "third-party-resources": [
      {
        "name": "[Vendor]",
        "usage-and-configuration": "[...]",
        "justification": "[...]",
        "mitigation-measures": "[...]",
        "compensating-controls": "[...]"
      }
    ]
  }
}
```
Notes:
- MAS-CSO-IIR: the cloud service offering is all information resources likely to handle federal customer data or likely to impact its confidentiality, integrity, or availability.
- MAS-CSO-FLO: document information flows and security categories for all resources; supply a machine-readable output, a human-readable explanation of how it is derived, and the code that generates it.
- MAS-CSO-TPR: for each third-party resource document general usage and configuration, justification, mitigation measures and compensating controls.
- Network architecture evidence relates to KSI-CNA-RNT and KSI-CNA-ULN; inventory evidence to KSI-PIY-GIV.

### 3. Policies reference (CDS-CSO-IRP)
For each policy and procedure: name, file or page name, brief summary, word count, current version, date of last update, related FedRAMP Practices (if applicable).

## Vulnerability Detection and Response Procedure (VDR and VER)

```markdown
# Vulnerability Detection and Response Procedure

## 1. Vulnerability Detection (VDR-CSO-DET)

Detection is not limited to scanning. Techniques include assessment, scanning, threat intelligence, vulnerability disclosure mechanisms, bug bounties, penetration testing, incident response, automated control testing and supply chain monitoring. An out-of-date control statement in the Security Decision Record is itself a vulnerability.

### Detection cadence (varies by Certification Class; take values from the rules)
- Resources likely to drift: VDR-TFR-PDD
- Resources not likely to drift: VDR-TFR-PCD
- Representative samples of similar machine-based resources: VDR-TFR-PSD
- Non-machine-based resources verified and validated at least every 3 months: VDR-TFR-NMV
- Machine-based resources verified and validated: VDR-TFR-MVX (20x) or VDR-TFR-MVF (Rev5)
- Automate detection (VDR-CSO-ADT) and detect after changes on representative samples (VDR-CSO-DAC)

### Detection sources
- Infrastructure: [Tool Name]
- Containers: [Tool Name]
- Code: [Tool Name]
- Dependencies and supply chain: [Tool Name]

## 2. Evaluation (VER-EVA-*)
For each detected vulnerability evaluate exploitability (VER-EVA-ELX), internet-reachability (VER-EVA-EIR) and Potential Agency Impact N-rating (VER-EVA-EPA); assume exploitation can be automated unless shown otherwise (VER-EVA-AIA); group vulnerabilities and evaluate false positives where useful (VER-EVA-GRV, VER-EVA-EFP). Evaluate within the VER-TFR-EVU timeframe for your Class.

## 3. Mitigation and Remediation Timeframes (VDR-TFR-PVR)
Timeframes depend on Certification Class, N-rating, internet-reachability and likely exploitability. Copy the table for your Class from the rule (read varies_by_class in the rules data). They are not CVSS severity buckets.

| N-rating | IRV + LEV | Not internet-reachable + LEV | Not likely exploitable |
|----------|-----------|------------------------------|------------------------|
| N2       | [days]    | [days]                       | [days]                 |
| N3       | [days]    | [days]                       | [days]                 |
| N4       | [days]    | [days]                       | [days]                 |
| N5       | [days]    | [days]                       | [days]                 |

Known Exploited Vulnerabilities follow the CISA KEV due dates (VDR-TFR-KEV, CISA BOD 26-04).

## 4. Response Process (VDR-CSO-RES)
1. Detection: automated or manual discovery
2. Evaluation: ratings per VER-EVA-*
3. Assignment: ticket and owner
4. Mitigation or remediation: partial mitigation, full mitigation or remediation
5. Validation: confirm the result
6. Reporting: VER-RPT-PER

## 5. Accepted Vulnerabilities (VER-TFR-MAV, VER-RPT-AVI)
A vulnerability not fully mitigated or remediated within 192 days of evaluation MUST be categorized as an accepted vulnerability. Report: tracking identifier, time and source of detection, time of evaluation, internet-reachable, likely exploitable, current N-rating, explanation of why it is accepted, and supplementary information for agencies.

## 6. Reporting (VER-RPT-*, VER-TFR-MHR)
- Report vulnerability detection and response activity at least monthly in a consistent human-readable format (VER-TFR-MHR)
- Include the VER-RPT-VDT fields for each vulnerability
- Do not irresponsibly disclose sensitive details (VER-RPT-NID)
- Vulnerability reports are FedRAMP Certification Data (VER-RPT-PER)
- Treat failures in this process as vulnerabilities (VDR-CSO-FAV)
```

## Incident Evaluation and Communication Procedure (IEC)

```markdown
# Incident Evaluation and Communication Procedure

## 1. Reportability Evaluation (IEC-CSO-EFR)
Promptly evaluate incidents to determine whether they affect, or are likely to affect, the confidentiality or integrity of federal customer data. Such incidents are FedRAMP Reportable Incidents. Keep an incident log showing the evaluation and reasons.

## 2. Potential Agency Impact N-rating (IEC-CSO-EFI, IEC-CSO-DPR)
- N1 likely minimal customer effect on 1 or more agencies
- N2 likely narrow customer effect on 1 or more agencies
- N3 likely disruptive effect on 1 agency
- N4 likely debilitating effect on 1 agency or disruptive effect on more than 1 agency
- N5 likely debilitating effect on more than 1 agency
Treat Reportable Incidents as N5 unless you promptly estimate the rating.

## 3. Reports and Timeframes (by Class and N-rating)
- Initial Incident Report (IEC-CSO-IIR)
- Ongoing Incident Reports (IEC-CSO-OIR)
- Final Incident Report (IEC-CSO-FIR)
Copy the timeframes for your Certification Class from the rules data (pain_timeframes). Requirement strength varies by Class (Class A: SHOULD for IIR and OIR; Class B, C and D: MUST; FIR is MUST for all).

## 4. Communication Channels (AFC)
- Maintain a FedRAMP Security Inbox and notify FedRAMP of address changes (AFC-CSO-INB, AFC-CSO-NOC)
- Treat email from @fedramp.gov or @gsa.gov as trusted (AFC-CSO-TFG)
- Receive and react without disruption (AFC-CSO-RCV)
- Route Emergency messages to a senior security official (AFC-CSO-EMR) and complete required actions (AFC-CSO-CRA)

## 5. Initial Incident Report Content (IEC-CSO-IIR)
- Contact information for the federal incident response coordinator
- Provider tracking identifier
- Description of the incident
- Timeline (start, detection time and source, completed reportability evaluation, other milestones)
- Historical and current N-rating with explanation
- Functional impact to federal agency customers
- Estimated recovery plan, milestones and timelines
- List of likely affected customer agencies

Use automation to minimize human intervention in reporting (IEC-CSO-AIR).

## 6. Post-Incident Activities (KSI-INR-AAR, KSI-INR-RPI)
- [ ] Generate the after action report and incorporate lessons learned
- [ ] Review past incidents for patterns
- [ ] Identify root cause
- [ ] Update procedures
- [ ] Record lessons learned for the next Ongoing Certification Report (CCM-OCR-AVL)
```

## Quick Reference: Required Documents

**Core Documents:**
1. Certification Package Overview (CPO-CSO-OVR)
2. Security Decision Record (SDR-CSO-FRR, SDR-CSX-KSI or SDR-CSF-CTF)
3. Vulnerability Detection, Response, Evaluation and Reporting Procedure (VDR, VER)
4. Incident Evaluation and Communication Procedure (IEC)
5. Significant Change Notification Procedure (SCN)
6. Ongoing Certification Report procedure (CCM-OCR-AVL)
7. KSI implementation documentation for all 46 KSIs

**Supporting Documents:**
8. Minimum Assessment Scope description (MAS)
9. Public information and trust center documentation (CDS)
10. Secure Configuration Guide (SCG-CSO-RSC, SCG-CSO-AUP)
11. Cryptographic module documentation (CMU-CSO-CMD)
12. FedRAMP Security Inbox procedures (AFC)

**Recurring Deliverables:**
13. Ongoing Certification Report every 3 months (CCM-OCR-AVL)
14. Quarterly Review materials (CCM-QTR-MTG, CCM-QTR-REG, CCM-QTR-NRD)
15. KSI metrics (SDR-CSX-KMT, by Class)
16. Vulnerability report at least monthly (VER-TFR-MHR)
17. Significant Change Notifications, 12 months retained (SCN-CSO-HIS)

Use get_control(requirement_id) to get specific requirement details for any documentation section.
